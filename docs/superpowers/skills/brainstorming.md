# brainstorming

**定位**：在任何创造性工作之前，把模糊想法通过协作对话提炼成经批准的设计/spec。

**触发条件**：创建功能、构建组件、添加功能、修改行为等任何需要写代码的创意工作之前。

---

## 核心流程

1. **探索项目上下文**：看文件、文档、最近提交。
2. **适时提供 Visual Companion**：第一次出现“看图比文字更清楚”的问题时，单独一条消息询问是否开启浏览器辅助；之前所有问题都在终端进行。
3. **逐个澄清问题**：一次只问一个，聚焦目的、约束、成功标准；优先用选择题。
4. **提出 2-3 种方案**：带权衡和你的推荐。
5. **分节呈现设计**：按复杂度调整篇幅，每节后确认。
6. **写入 design doc**：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，并提交。
7. **Spec 自检**：扫描占位符、内部一致性、范围、歧义。
8. **用户审查 gate**：让用户 review 书面 spec。
9. **过渡到 writing-plans**：这是本 skill 的唯一终点。

## 关键原则

- **HARD-GATE**：未经设计批准，不得调用任何实现 skill、写代码、搭项目。
- **没有“太简单”的例外**：再小的变更也要走流程，设计可以只有几句话。
- **YAGNI**：从所有设计中剔除不必要的功能。
- **一次只问一个问题**，避免信息过载。

## Visual Companion

浏览器可视化辅助，不是默认开启的模式。判断标准：**这个问题用户看到会比读到更清楚吗？**

- 用浏览器：mockup、wireframe、架构图、视觉对比。
- 用终端：需求、概念选择、权衡列表、技术决策。

详见 `refer/superpowers/skills/brainstorming/visual-companion.md`。

## 输出

- 经用户批准的书面 spec。
- 下一步固定调用 `writing-plans`。
