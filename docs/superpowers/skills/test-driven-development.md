# test-driven-development

**定位**：任何功能/bugfix 的实现方法：先写失败测试，再写最小实现，再重构。

**触发条件**：实现新功能、修复 bug、重构、修改行为之前。

---

## Iron Law

```
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

先写代码？删除它，重新开始。不许保留“参考”、不许“边写测试边适配”、不许看已有代码。

## Red-Green-Refactor

| 阶段 | 动作 | 验证 |
|---|---|---|
| **RED** | 写一个最小测试，展示期望行为 | 运行测试，确认它因功能缺失而失败 |
| **GREEN** | 写最小代码让测试通过 | 运行测试，确认通过；其他测试也不坏 |
| **REFACTOR** | 清理重复、改善命名、提取 helper | 保持测试全绿，不加新行为 |

## 好测试的标准

- **最小**：一个测试只测一件事；名字里出现 “and” 就拆分。
- **清晰**：名字描述行为。
- **真实**：尽量测真实代码，避免 mock；mock 只在不可避免时用。

## 为什么顺序重要

- “先实现后补测试”：测试立刻通过，无法证明它真的能抓 bug。
- “我已经手动测过所有边界”：手动测试无记录、不可复现、容易遗漏。
- “删掉 X 小时工作是浪费”：沉没成本谬误；保留无测试代码才是技术债。
- “TDD 太教条，我要务实”：TDD 才是务实——在提交前发现 bug，防止回归。

## Red Flags

- 先写代码后写测试。
- 测试一跑就通过。
- “这次例外”。
- “保留参考代码”。
- “Spirit not letter”。

## Bug Fix 流程

1. 写一个复现 bug 的测试，看到失败。
2. 最小修复。
3. 看到通过。
4. 回滚修复，确认测试再次失败；恢复修复，再次通过。
5. 重构（如需）。

## 卡住时

| 问题 | 解法 |
|---|---|
| 不知道怎么测 | 先写期望 API 和断言；问 human partner |
| 测试太复杂 | 设计太复杂，简化接口 |
| 必须 mock 一切 | 代码耦合，用依赖注入 |
| 测试 setup 巨大 | 提取 helper；仍然复杂则简化设计 |

## 相关

- `verification-before-completion`：claims 前验证。
- `systematic-debugging`：找 root cause 后写失败测试。
