# gc 未提交变更处理方案

## Problem Statement

执行 `gc` 时，当前工作区可能已存在未提交的变更（`git status` 不干净）。当前 `gc.md` 仅处理了"无变更"的情况，未覆盖"有未提交变更"的处理策略，导致流程可能意外中断或产生不期望的提交行为。

## Recommended Direction

在 `gc` 流程开头增加 **工作区预检** 步骤：

1. **检测**：执行 `git status --short`，判断工作区是否干净
2. **展示**：如不干净，输出精简的变更摘要（文件列表 + 状态标识）
3. **询问**：暂停并询问用户处理方式，默认选项为"将已有变更一并提交"
4. **执行**：用户确认后，统一执行 `git add .` → 正常走 gc commit 流程

交互示例：

```
检测到工作区存在未提交变更：
 M src/config.ts
?? docs/todo.md

处理方式：
1. 一并提交（默认）
2. 取消 gc，让我手动处理

选择 [1]: _
```

选择"一并提交"时，所有已有变更与新变更统一纳入本次 commit，使用用户输入的 commit message。

## Key Assumptions to Validate

- [ ] 用户看到变更摘要后，能正确判断这些变更是否应一起提交
- [ ] `git add .` 不会意外纳入敏感文件（依赖 `.gitignore` 和现有 secrets 自检）
- [ ] 合并提交的语义可被用户接受（原有变更 + 新变更共享同一 message）

## MVP Scope

**纳入：**
- `gc` 执行前 `git status` 检测
- 未提交变更的精简展示（`git status --short`）
- 交互式询问（默认选"一并提交"）
- `commands/gc.md` 文档更新，补充"工作区不干净"的处理分支

**不纳入：**
- 自动 stash / unstash（避免 pop 冲突导致工作丢失）
- 按文件粒度选择（超出 MVP，可后续扩展）
- 暂存区已有 staged 文件的特殊处理（假设用户要么全提要么不提）

## Not Doing (and Why)

- **自动 stash** — 违反"绝对不丢失工作"的硬约束，stash pop 可能产生冲突且用户无感知
- **静默自动 add + commit** — 用户可能未注意到已有变更被纳入，破坏可控性
- **分支隔离（为已有变更另开分支）** — 过度设计，用户明确反馈"默认补提交就行"
- **按文件粒度交互选择** — 增加复杂度，先验证最简单的主流程

## Open Questions

- 如果暂存区已有 staged 但未 commit 的变更，是否也走同样的"一并提交"逻辑？
- 是否需要为合并提交的场景在 commit message 中附加提示（如"含先前未提交变更"）？
- 是否需要限制变更数量阈值（如超过 20 个文件时强制手动处理）？
