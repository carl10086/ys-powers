Matt Pocock 的 Prompt 与 Skill，究竟干了什么

这不是 Matt 与 ys-powers 的比较页。它只解释：Matt 如何把“我要写一个功能”变成一组可以理解、拆分、实现、审查和恢复的工作。

阅读重点：不要把这些 skill 当成一串命令。Matt 真正设计的是一套“上下文如何流动、决策何时发生、代码任务如何被领取和完成”的 Prompt 协议。

一张图：Prompt 如何驱动写代码

蓝色是用户主动启动的流程入口，绿色是实现过程中被调用的底层能力，紫色是持续维护和反馈。

第一层：他怎样讨论问题

用户入口

grill-with-docs

skills/engineering/grill-with-docs/SKILL.md

它自己不负责提问。它只是规定：调用 grilling 和 domain-modeling。

Call the Skill tool twice, for "grilling" and "domain-modeling".

作用：把“讨论方案”和“维护领域语言”绑定在同一入口。

底层 Prompt

grilling

skills/productivity/grilling/SKILL.md

它把访谈变成一棵 design tree，只问当前已经具备前置条件的问题。

  • 每轮计算 frontier；
  • 每个问题附 recommended answer；
  • 环境事实由 agent 查询；
  • 设计决定由用户确认；
  • 所有分支走完才结束。
Ask the whole frontier in one round. Then wait for the user's answers.

作用：避免一次问错顺序，导致后面的设计建立在未确认的假设上。

底层 Prompt

domain-modeling

skills/engineering/domain-modeling/SKILL.md

它不负责写实现方案，而是负责把项目中的词变准确。

  • 发现术语与 glossary 冲突时立即指出；
  • 把模糊词变成 canonical term；
  • 用具体场景测试概念边界；
  • 对照代码检查说法是否真实；
  • 只有满足三个条件才创建 ADR。

作用：让 spec、ticket、test 使用同一套业务语言。

第二层：他怎样把讨论变成 spec 和任务

用户入口

to-spec

skills/engineering/to-spec/SKILL.md

它不再访谈。它假设前面的讨论已经完成，只负责综合和发布。

  • 先理解代码库；
  • 寻找最高层、最少的测试 seam；
  • 让用户确认 seam；
  • 按固定模板写 spec；
  • 发布到 issue tracker，并标记 ready-for-agent。
no interview, just synthesis of what you've already discussed.

作用：把“我们已经决定的东西”变成可交接的事实。

用户入口

to-tickets

skills/engineering/to-tickets/SKILL.md

它不把 spec 横向拆成“先数据库、再 API、再 UI”，而是切成完整的 tracer-bullet vertical slices。

  • 每个 ticket 都能独立 demo 或验证；
  • 每个 ticket 适合一个 fresh context；
  • 每个 ticket 标出 Blocked by；
  • 先让用户审核粒度和依赖；
  • 审核后才发布 ticket。
The tickets are not a list of steps. They are a task graph.

作用：让“下一件能做什么”变成系统状态，而不是模型记忆。

第三层：他怎样让 agent 写代码

用户入口

implement

skills/engineering/implement/SKILL.md
  • 读取 spec 或 ticket；
  • 调用 tdd；
  • 持续 typecheck 和单测；
  • 最后跑完整测试；
  • 调用 code-review；
  • 提交当前 branch。

作用：把实现流程写成固定协议，减少“写完代码就结束”。

用户入口

implement-spec

skills/engineering/implement-spec/SKILL.md

它是调度器，不是普通的“开始写代码”。

  • 读取 spec 和 task graph；
  • 找出当前 frontier；
  • 每个 ticket 启动 fresh implementer；
  • 每个 implementer 使用独立 worktree；
  • 由 merger 合并到 integration branch；
  • frontier 变化后继续启动新任务；
  • 全部完成后统一 code review。
Start every subagent with a fresh context window.

作用：把多个 ticket 变成可调度的并行工作，而不是把所有任务塞进一个上下文。

底层 Prompt

tdd

skills/engineering/tdd/SKILL.md
  • 只从 public interface 观察行为；
  • 测试 seam 必须提前确认；
  • 先 red，再 green；
  • 一次只做一个 slice；
  • 重构不放在 red-green 循环里。
One slice at a time. One seam, one test, one minimal implementation.

作用：约束模型不要先批量写测试或先做大规模实现。

第四层：他怎样审查结果

底层 Prompt

code-review

skills/engineering/code-review/SKILL.md

它刻意把 review 拆成两个互不覆盖的轴：

  • Standards：代码是否符合仓库规范；
  • Spec：代码是否实现了原始需求。

两个 fresh subagent 并行审查，最后并排报告。

Do not merge or rerank findings.

作用：防止“代码很漂亮”掩盖了“需求做错了”，也防止“功能做对了”掩盖了规范问题。

反馈 Prompt

retro

skills/engineering/retro/SKILL.md

它复盘的不是人的感受，而是 agent 环境应该如何改进。

  • Navigation：是否难以找到正确文件；
  • Automated checks：是否缺少可自动发现的检查；
  • Coding standards：是否需要新规则；
  • Tool economy：工具调用是否浪费；
  • No-ops：是否存在不改变行为的指令；
  • Information access：是否缺少关键信息。

作用：把一次实现中的问题，转成下一次运行环境的改进。

Matt 实际做的五个设计动作

1

把讨论变成设计树

不按感觉连续提问，而是只推进当前 frontier。

2

把决定变成 spec

to-spec 不重新发散，只综合已经确认的内容。

3

把 spec 变成 task graph

ticket 有依赖、有状态、有可领取的 frontier。

4

把实现隔离

fresh context、worktree、integration branch 分开上下文和代码变更。

5

把错误反馈回环境

code-review 找问题，retro 修改未来的工作方式。

完整 Skill 视图：不是都要执行

Matt 把 skill 分成“主流程入口”“模型按需调用”“用户遇到特殊任务时调用”和“实验/独立工具”。它们不是一条固定长链。

读取方法：先走核心代码流程；只有当前任务满足“什么时候用”条件，才加入下面的分支。setup-matt-pocock-skills 是一次性初始化，不是每个功能都重复运行。

Engineering：用户主动启动

用户入口

ask-matt

根据当前情况路由到合适的 Matt skill。

什么时候用：不知道该走哪个流程时。

用户入口

grill-with-docs

组合启动 grilling 与 domain-modeling。

什么时候用：开始讨论一个新方案或设计时。

用户入口

setup-matt-pocock-skills

配置 tracker、triage labels、GLOSSARY 和 ADR 布局。

什么时候用：每个 repo 第一次启用 Matt 时。

用户入口

to-spec

把已经讨论清楚的内容综合成 spec，并发布到 tracker。

什么时候用：设计决策已经确认后。

用户入口

to-tickets

把 spec 拆成 vertical-slice tickets 和 blocking edges。

什么时候用：spec 已经可以交给 agent 实现后。

用户入口

implement

实现单个 spec 或 ticket，完成测试、review 和 commit。

什么时候用：处理一个具体 ticket 时。

用户入口

implement-spec

读取整个 task graph，调度多个 ticket 到 integration branch。

什么时候用：完整实现一个包含多个 ticket 的 spec 时。

用户入口

wayfinder

为巨大且路线不清的工作建立 map 和 decision tickets。

什么时候用：工作超过一个 session，且还不知道完整路线时。

用户入口

triage

把 issue 从待分类状态推进到可交给 agent 或 human 的状态。

什么时候用：issue 来源杂乱、不能直接实现时。

用户入口

improve-codebase-architecture

扫描代码库，生成架构改进 HTML 报告，再选择一个方向讨论。

什么时候用：主动改善既有架构，而不是实现单个功能时。

用户入口

retro

复盘 agent 环境、导航、检查、工具和规则。

什么时候用：一次 coding session 完成后。

模型按需

模型按需

模型按需

模型按需

查高可信外部资料，并把结论保存为 cited Markdown。

凭证、第三方控制台或一次性 cutover 必须由人完成时。

一句话理解 Matt

Matt 不是主要在写“更多开发规范”；他是在用 Prompt 定义一套状态传递协议：什么已经决定、什么被谁阻塞、什么可以开始、什么证据证明完成、什么问题要反馈到环境。
来源文件均来自 refer/mattpocock-skills；本页面解释 Prompt 的职责和行为，不代表已经决定迁移或重写 ys-powers。
